# Module 2 — Fellow-to-Student Document Status "Revert" Communication

**Scope Status:** Out of Scope for the current phase (per Aug 18 scope confirmation). The spec below is fully resolved — zero open questions remain — and implementation-ready for whenever it is picked up.
**Priority (if scoped in):** Low — a small addition on top of Module 1 (Document Status Tracking), not new architecture.

---

**1. Feature/Module Name:** Fellow-to-Student Document Status "Revert" Communication

**2. Current State (Existing Wireframe Behavior):** Document status (Module 1) is visible to the student passively — a read-only status label per required document. There is no mechanism for a fellow to actively log a note or reason back to the student about a specific document.

**3. Requested Change:** Fellows can log a note against a specific document, visible to the student, with an in-app/portal notification alerting the student to check it.
- Confirmed: the note is a **separate log entry** — not merged into the status field itself (Module 1).
- Confirmed: notification is **in-app/portal only** — no SMS, no email.

**4. Business Objective:** Reduce reliance on ad hoc phone/WhatsApp follow-ups when a document is rejected or needs correction, by giving fellows a structured, auditable, in-portal way to flag it back to the student — and ensure the student actually notices, rather than relying on them to periodically re-check their document list on their own.

**5. Detailed Functional Requirements:**
- A fellow can add a note against any specific document (from Module 1's document list) at any time — structurally independent of, but typically used alongside, a status change.
- Each note is a discrete, timestamped log entry — not an edit to the document's `status` field.
- **[ASSUMPTION]** A note is fellow-initiated, not auto-generated by the system on every status change — i.e., changing status from "Applied" to "Follow-up in Progress" does not by itself create a log entry or notification unless the fellow deliberately adds one. This treats "separate log entry" as a genuinely distinct, deliberate action rather than an automatic byproduct of Module 1. Flag if every status change should auto-log instead.
- Creating a note triggers exactly one in-app/portal notification to the student. No SMS, no email — confirmed.
- A student can view all notes logged against their documents; notes are read-only to the student (they cannot edit or delete a fellow's note).
- Edge case: a document with zero notes logged should show a normal empty state — no notes section clutter, no "missing" implication.
- Edge case: if a fellow reassignment happens (a different fellow takes over a student), historical notes from the previous fellow remain visible and attributed to whoever logged them — not reassigned or hidden.

**6. UI/UX Changes Required:**
- Fellow view: a small "add note" action per document (text field + submit), separate from the status dropdown.
- Student view: notes logged against a document appear as a short timestamped list/thread under that document.
- Confirmed: the student sees the fellow's actual name on the note (not a generic "Fellow" label) — displayed from the `logged_by` Link field.
- Confirmed: a global notification bell surfaces that a new note exists (not an inline per-document badge).

**7. Data Requirements:**
**[ASSUMPTION — proposed structure, confirm against schema]** A new child table, "Document Communication Log," on the Scholarship Application (sibling to Module 1's "Application Document" table):

| Field | Type | Notes |
|---|---|---|
| `document_type` | Select/Link | Which required document this note is about — mirrors Module 1's `document_type` so the note maps back to the right row |
| `note` | Small Text | The fellow's message |
| `logged_by` | Link → User | Defaults to session user (the fellow) |
| `logged_on` | Datetime | Defaults to now |
| `notification_sent` | Check | Internal flag — prevents double-notifying on re-save |

Relationship: Scholarship Application (1) → Document Communication Log (N).

**8. Acceptance Criteria:**
- A fellow can add a note against any document; the note is stored as a distinct record, never written into the document's status field.
- The student sees the note against the correct document, with no ability to edit or delete it.
- Exactly one in-app/portal notification is generated per note; no SMS or email is ever sent by this module.
- Notes persist and remain correctly attributed even if the student's assigned fellow changes later.

**9. Technical Considerations:**
- Confirmed: use Frappe's built-in `Notification Log` system for the in-app alert, rather than a custom-built indicator. If students access this via Frappe's portal/website pages rather than the desk UI, surfacing the standard Notification Log there is a small, known build step — not an open question anymore. Exact API call should be confirmed against the installed Frappe version at implementation time.
- Frappe's generic `Comment`/`Communication` doctypes were considered as a reuse option (avoid building new infrastructure where Frappe already has something) but set aside: they attach to a whole document, not to a specific child-table row (i.e., not to one specific document within the application), and are desk-oriented by default — both mismatches to this requirement.
- Because this is a child table (not a standalone DocType), detecting "a new row was added" to trigger the notification requires comparing old vs. new child-table state in the parent's `on_update` hook — a standalone DocType would allow a simpler `after_insert` hook instead (see trade-off below).
- **Trade-off for the developer to weigh:** child table (simpler data model, slightly more involved hook logic to detect new rows) vs. a standalone DocType with an `application` Link field (cleaner `after_insert` hook, one more DocType to manage). Either is workable; child table is the default recommendation below for consistency with Module 1's pattern.

**10. Priority Level:** Not prioritized — Out of Scope for the current phase. If scoped in: **Low**, since it's additive to Module 1 rather than new architecture.

**11. Implementation Recommendation:** New child table ("Document Communication Log") on the existing Scholarship Application DocType, sibling to Module 1's "Application Document" table. On save, diff child-table rows for new entries with `notification_sent = 0`, then create a `Notification Log` record targeting the student user and set the flag. Both previously open questions are now resolved — this module's spec is fully locked and ready for CLI.
